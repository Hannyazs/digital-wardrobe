## Contexto

As imagens existentes estão em `uploads/` e os registros apontam para `/uploads/<arquivo>`. Se os dados atuais forem a preservar (decisão da E9.F1.2), as imagens precisam ir para o bucket, no caminho do usuário definitivo.

## Descrição

- **Se os dados atuais forem descartáveis** (decisão da E9.F1.2), esta PBI se reduz ao registro dessa decisão.
- Se não: plano e script idempotente que sobe cada arquivo para `{usuario_id}/...`, atualiza o `imagem_url` e só então marca como migrado.
- `--dry-run` por padrão, relatório por tabela e verificação de existência no destino.
- `uploads/` não é apagado.

**Esta PBI entrega o plano e o script; nada é executado.** A execução é a E10.F4.2.

## Escopo

**Dentro:** script e plano para `pecas.imagem_url` e `referencias.imagem_url`; relatório; documento de reversão.

**Fora de escopo:** executar; desligar o acesso público a `/uploads` (E10.F4.2); apagar arquivos locais.

## Como será feito

- Para cada registro com valor `/uploads/...`: ler o arquivo local, enviar ao bucket com a chave `{usuario_id}/{pecas|referencias}/{nome}`, conferir a existência e o tamanho no destino, só então atualizar o registro (por registro, em transação curta).
- Idempotente: registro já com chave do storage é pulado; reexecutar não duplica.
- Arquivo local ausente fica no relatório como "órfão de registro" e não interrompe o resto.
- Backup do banco como pré-condição, como na E9.F1.2.
- Usa o `usuario_id` já migrado (E9.F1.3), para o caminho não nascer com o UUID de desenvolvimento.

## Critérios de aceite

- Dado `--dry-run`, então lista o que seria enviado e atualizado, sem alterar bucket nem banco.
- Dada uma execução em ambiente de teste, então cada registro migrado aponta para um arquivo existente no destino.
- Dada uma segunda execução, então nada é duplicado.
- Dado um arquivo local ausente, então vai para o relatório e o resto segue.
- Dada a conclusão, então `uploads/` permanece intacto.

## Definição de pronto

- [ ] Script testado só em banco e bucket de teste/dry-run; **nenhuma execução no ambiente real**.
- [ ] Plano de reversão documentado.
- [ ] Status deste arquivo e do `backlog.md` atualizado.

## Riscos e pontos de atenção

- Atualizar o registro antes de confirmar o arquivo deixaria imagens quebradas; a ordem acima evita isso.
- Consumo do plano gratuito: o tamanho total de `uploads/` precisa caber nos limites registrados na E10.F1.1.

## Como testar

1. Montar um conjunto de teste com arquivos e registros fictícios.
2. Rodar `--dry-run`, depois a execução no ambiente de teste, depois repetir.
3. Abrir os registros pela API e conferir as imagens.
