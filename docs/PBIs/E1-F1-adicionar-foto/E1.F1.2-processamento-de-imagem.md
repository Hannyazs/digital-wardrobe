## Contexto

Esta PBI é o lado backend do mesmo fluxo que a E1.F1.1 iniciou no app: depois que o usuário escolhe uma foto, alguém precisa de fato remover o fundo antes de qualquer outra coisa acontecer (metadados, confirmação de cadastro). É a segunda perna da feature "Adicionar peça por foto" (ver [arquitetura.md](../../arquitetura.md), seção "Cadastro de peça") — sem ela, a E1.F1.3 (que liga app e backend) não tem o que chamar.

Para a persona Marina, essa etapa é a promessa central do produto: ela tira uma foto qualquer, de qualquer fundo, e o app entrega uma imagem com aparência de catálogo, sem ela precisar editar nada.

## Descrição

Implementar (e fechar as lacunas já identificadas em) o endpoint `POST /pecas/processar-imagem`, que:
1. Recebe a foto via multipart.
2. Remove o fundo via `rembg`.
3. Salva o resultado no storage local e devolve a URL.
4. Em caso de imagem inválida ou falha do `rembg`, devolve um erro HTTP estruturado — nunca uma exception crua — e loga o erro no backend.

O código do caminho feliz (passos 1–3) já existe e está corretamente encadeado (`pecas.py` → `image_service.py` → `rembg_adapter.py`/`storage_adapter.py`), mas nunca foi executado com uma imagem real, e o passo 4 (tratamento de erro) ainda não foi implementado — é o que falta pra fechar esta PBI.

**Esta PBI para na resposta do endpoint.** Ela não decide o que o app faz com a URL devolvida (isso é a E1.F1.3) nem como o app reage a um erro vindo daqui (isso é a E1.F1.4) — só garante que o contrato HTTP do backend é bem-comportado nos dois casos.

## Escopo

**Dentro do escopo:**
- Endpoint `POST /pecas/processar-imagem` (multipart), já existente — validar seu comportamento.
- Chamada ao `rembg_adapter` para remover o fundo e ao `storage_adapter` para persistir o resultado (local, `backend/uploads/`).
- Tratamento estruturado de erro: imagem inválida/corrompida **e** falha do `rembg` por qualquer outro motivo → `HTTPException` com log no backend, nunca um 500 cru.
- Rodar o processamento (CPU-bound) fora do event loop principal — achado de dívida técnica já registrado no backlog (`processar_imagem_peca` é síncrona e hoje é chamada direto dentro de uma rota `async def`, bloqueando o loop inteiro). Resolvido junto por estar na mesma linha de código do try/except e ser trivial de corrigir agora.
- Validação manual do caminho feliz com uma imagem real (subir a API, enviar a foto, conferir o PNG e a URL).

**Fora do escopo (não implementar aqui):**
- O que o app Flutter faz com a resposta (sucesso ou erro) — isso é **E1.F1.3** (exibir o resultado) e **E1.F1.4** (degradação graciosa no app quando o backend falha). Este PBI cobre só o contrato HTTP do backend.
- Chamada real ao Gemini Vision para sugestão de metadados. `image_service.py` já chama `gemini_adapter.extract_metadata`, mas esse adapter é um stub deliberado que sempre devolve uma sugestão vazia (comentário `TODO` no próprio arquivo) — isso é do **Épico 5** (cadastro assistido por IA) e não deve virar chamada real aqui.
- Mover o processamento pra uma fila/worker separado do processo da API (ex: Celery/RQ). O CLAUDE.md já prevê isso ("devem rodar fora do request HTTP... conforme o volume de usuários crescer"), mas para o estágio atual do produto (MVP local, um usuário por vez em teste), despachar a chamada síncrona num threadpool (ver "Como será feito") é suficiente.
- Trocar o storage local por S3/Supabase — fica para quando o ambiente de produção exigir (ver arquitetura.md, "Storage de imagens").

## Como será feito

### Tratamento de erro

Duas exceções de domínio novas em `backend/app/core/exceptions.py` (novo arquivo, não em `adapters/rembg_adapter.py`): se o provedor de remoção de fundo for trocado no futuro, o router não deveria precisar importar um tipo de exceção específico do rembg — mesmo racional da regra de camadas do CLAUDE.md ("routers não chamam adapters diretamente").

- `ImagemInvalidaError` — a imagem recebida não é um formato que o PIL consegue decodificar.
- `ProcessamentoImagemError` — qualquer outra falha durante a remoção de fundo em si.

Em `rembg_adapter.remove_background`:
```python
try:
    imagem_original = Image.open(BytesIO(imagem_bytes))
    imagem_original.load()  # Image.open é lazy; só falha de fato ao decodificar o pixel
except UnidentifiedImageError as exc:
    raise ImagemInvalidaError("Imagem inválida ou corrompida.") from exc

try:
    imagem_processada = remove(imagem_original)
except Exception as exc:
    raise ProcessamentoImagemError("Falha ao remover o fundo da imagem.") from exc
```
O `except Exception` amplo ao redor de `remove()` é deliberado: uma imagem que o PIL abre sem erro ainda pode quebrar o modelo do rembg (ex: modos de cor incomuns), e o critério de aceite pede cobertura para "qualquer motivo".

Em `app/api/v1/pecas.py`, traduzir para HTTP e logar:
```python
try:
    return await run_in_threadpool(processar_imagem_peca, imagem_bytes)
except ImagemInvalidaError as exc:
    raise HTTPException(status_code=422, detail=str(exc)) from exc
except ProcessamentoImagemError as exc:
    logger.error("Falha ao processar imagem", exc_info=exc)
    raise HTTPException(status_code=500, detail="Falha ao processar a imagem. Tente novamente.") from exc
```
A mensagem do 500 é genérica de propósito — não vaza detalhe interno pro cliente; o `logger.error` com `exc_info` é o único lugar onde a causa raiz fica visível.

### Bloqueio do event loop (achado de dívida técnica do backlog)

`processar_imagem_peca` continua uma função síncrona — faz sentido, já que PIL e `rembg` são bibliotecas síncronas. O que muda é como a rota a invoca: `await run_in_threadpool(processar_imagem_peca, imagem_bytes)` em vez de chamá-la direto. `run_in_threadpool` vem de `fastapi.concurrency`, sem dependência nova no `requirements.txt`.

Alternativa considerada e descartada: tornar a rota `def` em vez de `async def` (FastAPI despacha rotas síncronas em threadpool automaticamente). Descartada porque a rota já faz `await arquivo.read()` — I/O assíncrono de leitura do upload —, então precisa continuar `async def`; `run_in_threadpool` é a opção que preserva as duas coisas.

### Arquivos afetados

- `backend/app/core/exceptions.py` — novo (`ImagemInvalidaError`, `ProcessamentoImagemError`).
- `backend/app/adapters/rembg_adapter.py` — try/except em volta de `Image.open`/`.load()` e de `remove()`.
- `backend/app/api/v1/pecas.py` — try/except traduzindo pra `HTTPException`, `logging.getLogger(__name__)`, `run_in_threadpool` em vez da chamada direta.
- Sem mudança em `image_service.py`, `storage_adapter.py` ou `schemas/peca.py` — o contrato de resposta do caminho feliz não muda.

## Critérios de aceite

- **Dado** um arquivo de imagem válido enviado via multipart, **quando** o cliente chama `POST /pecas/processar-imagem`, **então** a resposta é 200 com a URL de um PNG com fundo removido, acessível em `/uploads/<nome>.png`.
- **Dado** um arquivo que não é uma imagem válida (corrompido ou formato não suportado), **quando** o cliente chama o endpoint, **então** a resposta é um erro HTTP estruturado (422) com uma mensagem, e o erro é logado no backend — nunca uma exception crua (500 sem tratamento).
- **Dado** que o `rembg` falha ao processar uma imagem por qualquer outro motivo, **quando** isso acontece, **então** a resposta é um erro HTTP estruturado (500) com uma mensagem genérica, e a causa raiz (com stack trace) é logada no backend.
- **Dado** que uma requisição está processando uma imagem (etapa CPU-bound), **quando** outra requisição chega à API ao mesmo tempo, **então** ela não fica bloqueada esperando a primeira terminar (achado de dívida técnica do backlog, não um critério de aceite original — incluído aqui por ser resolvido junto).

## Riscos e pontos de atenção

- O `rembg` baixa o modelo de ML (`u2net`, ~176MB) na primeira execução — a primeira chamada real vai demorar bem mais que as seguintes; ao validar manualmente, não confundir isso com travamento ou timeout.
- Distinguir "imagem inválida" de "rembg falhou" na prática é mais nebuloso do que a categorização sugere — o `except Exception` amplo ao redor de `remove()` é intencionalmente largo por isso, mas pode capturar mais do que o esperado (ex: erro de memória) sob o mesmo código de erro genérico.
- Sem suíte de testes automatizados no backend ainda (ver CLAUDE.md) — toda a validação desta PBI é manual; não há rede de segurança pra regressões futuras nesse endpoint.
- `ImagemProcessadaResponse` já inclui `sugestao` (Gemini) mesmo sendo um stub vazio — isso é anterior a esta PBI e pertence ao Épico 5; só registrado aqui para não ser confundido com escopo deste PBI.
- Este critério de aceite (erro tratado) já causou confusão de escopo antes com a **E1.F1.4** — reforçando: esta PBI garante que o **backend nunca devolve um 500 cru**; a E1.F1.4 é sobre como o **app** se comporta ao receber esse erro.

## Como testar

1. Subir o ambiente: `docker compose up -d` (raiz do repo), depois em `backend/`: `alembic upgrade head` e `uvicorn app.main:app --reload`.
2. **Caminho feliz**: enviar uma foto real (note o prefixo `/api/v1`, definido em `app/api/v1/router.py` — a descrição resumida em `backlog.md` omite esse prefixo).
   ```bash
   curl -X POST http://localhost:8000/api/v1/pecas/processar-imagem -F "arquivo=@caminho/para/foto.jpg"
   ```
   Conferir: resposta 200, campo `imagem_url` no formato `/uploads/<uuid>.png`, e que abrir `http://localhost:8000/uploads/<uuid>.png` mostra a peça com fundo transparente.
3. **Caminho de erro — imagem inválida**: enviar um arquivo que não é imagem (ex: um `.txt` renomeado para `.jpg`). Conferir resposta 422 estruturada (não um 500 com traceback do FastAPI) e que o erro aparece no log do `uvicorn --reload`.
4. **Caminho de erro — falha do rembg**: difícil de forçar deterministicamente com uma imagem real (testado com imagens 1x1 e CMYK nesta implementação — o rembg processou ambas sem erro). Verificado em vez disso com um mock de `app.adapters.rembg_adapter.remove` levantando uma exceção, via `unittest.mock.patch` + `TestClient` do FastAPI, exercitando o endpoint real de ponta a ponta (ver Log de implementação) — cobre a tradução pra 500 e o log, mesmo sem uma imagem real que quebre o rembg.
5. **Concorrência** (evidência do fix de threadpool): disparar a chamada do passo 2 e, enquanto ela processa, fazer `curl http://localhost:8000/` (health check) em outro terminal — a segunda requisição deve responder imediatamente, sem esperar a primeira terminar.

Nenhum desvio do "Como será feito" da PBI — implementado exatamente como documentado.

### Verificação realizada (execução real, não presumida)

Sem suíte `pytest` configurada no backend (confirmado — nada em `requirements.txt`), a verificação foi feita subindo a API de verdade (`uvicorn`, sem depender do Postgres/Docker, já que o endpoint testado não toca o banco) e também exercitando o router por dentro com `TestClient` para os casos difíceis de reproduzir via HTTP puro:

1. **Caminho feliz** — API local rodando (`uvicorn app.main:app`, porta livre), imagem JPEG real gerada com PIL enviada via `curl -F`. Resposta `200`, `imagem_url` no formato `/uploads/<uuid>.png`; o arquivo foi baixado de volta e reaberto com PIL — confirmado `format=PNG`, `mode=RGBA` (fundo removido/transparente), `size=(200, 200)`.
2. **Imagem inválida (422)** — enviado um arquivo texto renomeado `.jpg`. Resposta `422` com `{"detail": "Imagem inválida ou corrompida."}`; log do backend mostrou a linha `WARNING ... Imagem inválida recebida em /processar-imagem: ...` — confirma que o terceiro critério de aceite (erro tratado + logado) está implementado, o gap que o backlog apontava.
3. **Falha do rembg (500)** — duas imagens de borda reais (1x1 pixel e CMYK) foram enviadas esperando quebrar o rembg; **ambas foram processadas com sucesso (200)** — o modelo se mostrou mais robusto do que o esperado, então não deu pra forçar esse caminho com uma imagem real. Em vez disso, verificado com `unittest.mock.patch("app.adapters.rembg_adapter.remove", side_effect=RuntimeError(...))` + `fastapi.testclient.TestClient` chamando o endpoint real (`/api/v1/pecas/processar-imagem`) — confirmado `500` com `{"detail": "Falha ao processar a imagem. Tente novamente."}` e log `ERROR ... Falha ao processar imagem` com o traceback completo (`RuntimeError: falha simulada` como causa, via `from exc`). Cobre o comportamento do endpoint de ponta a ponta sem exigir um teste automatizado permanente, que estaria fora do escopo desta PBI.
4. **Concorrência (event loop não bloqueado)** — disparada a chamada de processamento (~2,5s, medido) em background e, imediatamente, um `GET /` — respondeu em `0.003s` enquanto a primeira ainda processava. Confirma que `run_in_threadpool` resolveu o achado de dívida técnica do backlog.
5. Também confirmado à parte (fora do servidor HTTP, direto no adapter): `rembg_adapter.remove_background` levanta `ImagemInvalidaError` para bytes que não são imagem, e `ProcessamentoImagemError` (com `__cause__` preservado) quando `remove()` falha.

### Mudanças de escopo (fora do que a PBI original documentava)

1. **Log também no caminho 422, não só no 500** — a PBI documentava em "Como será feito" apenas `logger.error` para `ProcessamentoImagemError`; o critério de aceite, porém, também pede log para o caso de imagem inválida ("o erro é logado no backend"). Adicionado `logger.warning` nesse caminho durante a implementação, para não deixar o próprio critério de aceite desta PBI sem cobertura. Pequeno, documentado aqui em vez de silencioso.
2. **Correção de um erro na própria PBI**: a seção "Como testar" (escrita na criação da PBI) usava `http://localhost:8000/pecas/processar-imagem`, sem o prefixo `/api/v1` que `app/api/v1/router.py` já define. Descoberto ao executar o teste manual de verdade (`404 Not Found`) — corrigido no arquivo desta PBI para `/api/v1/pecas/processar-imagem`. Não é uma mudança de comportamento do código, só uma correção de documentação.
3. **Limpeza dos artefatos de teste**: os PNGs gerados nos testes manuais (`backend/uploads/*.png`) foram apagados ao final — são artefatos de verificação, não deveriam ficar no diretório de uploads de desenvolvimento.

### Decisões de implementação não detalhadas antes

- O servidor de verificação foi iniciado sem depender do Postgres/Docker Compose (o `create_async_engine` do SQLAlchemy é lazy — só conecta quando uma rota que toca o banco é chamada, e `/processar-imagem` não toca). Permitiu validar esta PBI isoladamente, sem subir o ambiente inteiro.
- Para o caso de falha do rembg (item 3 da verificação), usar `TestClient` + mock foi uma escolha deliberada em vez de tentar mais combinações de imagem — o objetivo era verificar o comportamento do endpoint (tradução de exceção → HTTP → log), não encontrar um caso real que quebre o modelo do rembg, que é um problema de outra natureza.
