## Contexto

Lado backend do fluxo iniciado pela E1.F1.1: depois que o usuário escolhe uma foto, alguém precisa remover o fundo antes de qualquer outra coisa. Sem isso, a E1.F1.3 (que liga app e backend) não tem o que chamar.

## Descrição

Fechar as lacunas do endpoint `POST /pecas/processar-imagem`: recebe foto multipart → remove fundo via `rembg` → salva no storage e devolve URL → em erro (imagem inválida ou falha do rembg), devolve HTTP estruturado, nunca exception crua, com log.

O caminho feliz já existia e estava corretamente encadeado, mas nunca executado com imagem real; o tratamento de erro é o que faltava.

**Para na resposta do endpoint** — não decide o que o app faz com a URL (E1.F1.3) nem como reage a erro (E1.F1.4).

## Escopo

**Dentro do escopo:**
- Validar o endpoint existente com imagem real.
- Tratamento estruturado de erro (imagem inválida **e** falha do rembg por qualquer motivo) → `HTTPException` + log, nunca 500 cru.
- Despachar o processamento (CPU-bound) fora do event loop — dívida técnica já registrada no backlog, resolvida junto por ser trivial na mesma linha de código.
- Validação manual do caminho feliz com imagem real.

**Fora do escopo:**
- Reação do app ao resultado/erro — E1.F1.3/E1.F1.4.
- Chamada real ao Gemini Vision — `gemini_adapter` continua stub (Épico 5).
- Fila/worker separado (Celery/RQ) — threadpool já é suficiente no estágio atual.
- Trocar storage local por S3/Supabase — fica para quando produção exigir.

## Como será feito

- Duas exceções novas em `app/core/exceptions.py` (não em `rembg_adapter.py`, para não acoplar o router a um tipo de erro do rembg): `ImagemInvalidaError`, `ProcessamentoImagemError`.
- `rembg_adapter.remove_background`: `Image.open`/`.load()` capturando `UnidentifiedImageError` → `ImagemInvalidaError`; `remove()` com `except Exception` amplo (deliberado — cobre "qualquer motivo") → `ProcessamentoImagemError`.
- Router traduz para HTTP: `ImagemInvalidaError` → 422, `ProcessamentoImagemError` → 500 genérico + `logger.error(exc_info=...)`.
- Chamada despachada via `run_in_threadpool` (de `fastapi.concurrency`) em vez de direta — a rota precisa continuar `async def` por já fazer `await arquivo.read()`.

**Arquivos afetados**: `app/core/exceptions.py` (novo), `app/adapters/rembg_adapter.py`, `app/api/v1/pecas.py`.

## Critérios de aceite

- Imagem válida via multipart → 200 com URL de PNG sem fundo em `/uploads/<nome>.png`.
- Arquivo inválido/corrompido → 422 estruturado + log, nunca 500 cru.
- Falha do rembg por outro motivo → 500 genérico + causa raiz logada (stack trace).
- Requisição em processamento não bloqueia outra requisição simultânea.

## Riscos e pontos de atenção

- `rembg` baixa o modelo (~176MB) na primeira execução — não confundir isso com travamento ao validar.
- `except Exception` amplo ao redor de `remove()` pode capturar mais que o esperado (ex: erro de memória) sob o mesmo código genérico.
- Sem suíte de testes automatizados no backend ainda — toda validação aqui é manual.
- `ImagemProcessadaResponse.sugestao` (Gemini) é stub vazio — pertence ao Épico 5, não confundir com escopo desta PBI.

## Como testar

1. `docker compose up -d` (raiz), depois em `backend/`: `alembic upgrade head`, `uvicorn app.main:app --reload`.
2. Caminho feliz: `curl -X POST http://localhost:8000/api/v1/pecas/processar-imagem -F "arquivo=@foto.jpg"` → 200, `imagem_url` em `/uploads/<uuid>.png`, imagem com fundo transparente.
3. Imagem inválida: enviar um `.txt` renomeado `.jpg` → 422 estruturado (não traceback do FastAPI), erro no log do `uvicorn`.
4. Falha do rembg: difícil forçar com imagem real — usar mock de `rembg_adapter.remove` + `TestClient` para exercitar o 500 e o log.
5. Concorrência: disparar o passo 2 e, em paralelo, `curl http://localhost:8000/` — deve responder de imediato.

## Log de implementação

**Entregue**: exatamente como "Como será feito" — `exceptions.py` novo, `try/except` em `rembg_adapter.py` preservando causa (`from exc`), router traduzindo para 422/500 com log (`warning`/`error`), `run_in_threadpool` no lugar da chamada direta.

**Verificação real** (sem `pytest` configurado, API local de verdade + `TestClient` para os casos difíceis): caminho feliz confirmado (200, PNG RGBA 200×200 transparente); imagem inválida confirmada (422 + log `WARNING`); falha do rembg forçada via mock (`side_effect=RuntimeError`) + `TestClient` → 500 + log `ERROR` com `exc_info`, já que duas imagens de borda reais (1×1, CMYK) processaram sem erro; concorrência confirmada (`GET /` respondeu em 0.003s enquanto o processamento de ~2.5s rodava).

**Mudanças de escopo**: (1) log também adicionado no caminho 422 (`logger.warning`), não só no 500 — a PBI original só previa log para `ProcessamentoImagemError`, mas o próprio critério de aceite exige log nos dois casos. (2) corrigido `/pecas/...` → `/api/v1/pecas/...` na seção "Como testar" (erro de documentação, não de código). (3) PNGs de teste apagados de `backend/uploads/` ao final.

**Pendente**: nenhum item dos critérios de aceite/DoD — todos executados e observados. Resta o já registrado em Riscos: sem teste automatizado permanente.
