## Contexto

Esta PBI é a cola entre as duas pernas já prontas da feature: o app já sabe capturar/selecionar uma foto (E1.F1.1) e o backend já sabe processá-la (E1.F1.2). Nenhuma das duas conversa com a outra ainda — o botão "Confirmar" da tela de upload está desabilitado com um `// TODO(E1.F1.3)`, e o `PecaService.processarImagem` existe mas nunca é chamado de lugar nenhum.

Para a persona Marina, é o momento em que a "mágica" do produto acontece de verdade: ela vê a foto que tirou virar uma imagem de catálogo, sem fazer nada além de esperar alguns segundos.

## Descrição

Ligar o botão "Confirmar" da tela de upload à chamada real de `POST /pecas/processar-imagem`, cobrindo:
1. Estado de carregamento visível enquanto a requisição está em andamento.
2. Exibição da imagem processada (sem fundo) quando a resposta chega com sucesso.
3. Uma mensagem de erro clara — sem travar a tela nem deixar o carregamento girando para sempre — se a requisição falhar por qualquer motivo (rede, timeout, ou erro HTTP vindo do backend).

**Esta PBI para na exibição do resultado.** Não decide o que fazer com a peça a partir daí (isso é a Feature 2, preenchimento de metadados + `POST /pecas`) e não implementa nenhuma ação de recuperação específica pro caso de falha do processamento além de "avisar e deixar tentar de novo" — a ação de "seguir com a foto original sem remoção de fundo" é da **E1.F1.4**.

## Escopo

**Dentro do escopo:**
- Habilitar o botão "Confirmar" na tela de upload para disparar o envio da foto já selecionada (E1.F1.1).
- Indicador de carregamento (`CircularProgressIndicator`) visível durante a chamada.
- Exibir a imagem processada (`imagem_url` da resposta) ao concluir com sucesso.
- Capturar qualquer falha da chamada (erro de rede, timeout, ou resposta HTTP de erro do backend — 422/500 da E1.F1.2) e mostrar uma mensagem genérica de erro com opção de "tentar novamente", sem travar a tela.
- Corrigir `PecaService.processarImagem` para funcionar no Chrome (ver "Como será feito" — hoje usa `dart:io File`, que quebra em Web).
- Configurar timeout explícito no `Dio` (`ApiClient`) — sem isso, o critério de aceite "timeout mostra mensagem clara" não tem como ser exercitado, porque o Dio nunca desiste sozinho.

**Fora do escopo (não implementar aqui):**
- Diferenciar reação por tipo de falha (estruturada do backend vs. timeout de rede) e oferecer "seguir sem remoção de fundo" — isso é **E1.F1.4**. Esta PBI trata toda falha de forma genérica (mensagem + tentar novamente); a E1.F1.4 é quem enriquece essa reação para os dois casos que ela cobre. Esse limite já causou confusão de escopo antes entre E1.F1.2 e E1.F1.4 no projeto — reforçando aqui para não repetir com a E1.F1.3.
- Revisão/edição dos metadados sugeridos (`sugestao` da resposta) e o `POST /pecas` final — Feature 2 do Épico 1.
- Qualquer mudança no contrato do endpoint `/pecas/processar-imagem` — já fechado pela E1.F1.2.
- Rodar o processamento em background/fila (Celery/RQ) — decisão já registrada como não aplicável ao estágio atual do projeto (ver `arquitetura.md`).

## Como será feito

### Gerenciamento de estado

Reaproveitar o `uploadPhotoProvider` (`Notifier<XFile?>`) da E1.F1.1 para ler a foto já selecionada — não duplicar esse estado. Adicionar um segundo `Notifier` só para o ciclo de envio, no mesmo arquivo `upload_controller.dart`:

```dart
sealed class EnvioState {}
class EnvioIdle extends EnvioState {}
class Enviando extends EnvioState {}
class EnvioSucesso extends EnvioState { final String imagemUrl; }
class EnvioErro extends EnvioState { final String mensagem; }

class UploadSubmissionController extends Notifier<EnvioState> {
  @override
  EnvioState build() => EnvioIdle();

  Future<void> enviar() async {
    final foto = ref.read(uploadPhotoProvider);
    if (foto == null) return;
    state = Enviando();
    try {
      final resultado = await ref.read(pecaServiceProvider).processarImagem(foto);
      state = EnvioSucesso(imagemUrl: resultado['imagem_url'] as String);
    } on DioException catch (e) {
      state = EnvioErro(_mensagemDeErro(e));
    } catch (_) {
      state = EnvioErro('Não foi possível processar a foto. Tente novamente.');
    }
  }
}
```

Dois providers separados (foto vs. envio) porque têm ciclos de vida diferentes: trocar a foto (`uploadPhotoProvider.clear()`) deve poder resetar o envio, mas o inverso não é verdade — um erro de envio não deve descartar a foto escolhida (o usuário precisa poder tentar de novo sem escolher a foto outra vez).

### Correção necessária: `PecaService.processarImagem` não funciona em Web

`peca_service.dart` hoje recebe um `dart:io File` e chama `MultipartFile.fromFile(imagem.path)`. Isso quebra no Chrome — mesmo ponto de atenção já registrado na E1.F1.1 (`dart:io File` não existe em Flutter Web) — e a E1.F1.1 corretamente evitou `File` na tela, mas o `PecaService` ainda o exige na assinatura. Como o Chrome é a única plataforma validada no momento, esse é um bloqueio real para testar esta PBI, não hipotético.

Trocar a assinatura para receber `XFile` (do `image_picker`, já usado pela tela) e montar o multipart a partir dos bytes, que funciona igual em mobile e Web:

```dart
Future<Map<String, dynamic>> processarImagem(XFile imagem) async {
  final bytes = await imagem.readAsBytes();
  final formData = FormData.fromMap({
    'arquivo': MultipartFile.fromBytes(bytes, filename: imagem.name),
  });
  final response = await _dio.post('/pecas/processar-imagem', data: formData);
  return response.data as Map<String, dynamic>;
}
```

Isso é um achado de bloqueio pré-existente (não introduzido por esta PBI), corrigido aqui porque impede a própria PBI de ser verificada — mesmo racional já usado na E1.F1.2 para o bloqueio do event loop.

### Timeout no `ApiClient`

`Dio` não tem timeout nenhum configurado hoje (`BaseOptions(baseUrl: ...)` só). Sem isso, uma requisição pendurada nunca aciona o caminho de "timeout" — ela fica esperando indefinidamente, e o critério de aceite correspondente não é verificável. Adicionar:

```dart
BaseOptions(
  baseUrl: AppConstants.apiBaseUrl,
  connectTimeout: const Duration(seconds: 15),
  sendTimeout: const Duration(seconds: 60),
  receiveTimeout: const Duration(seconds: 60),
)
```

`sendTimeout`/`receiveTimeout` em 60s (não os 30s cogitados inicialmente numa tentativa anterior desta implementação) — a E1.F1.2 registrou que a primeira chamada ao `rembg` baixa um modelo de ~176MB e demora bem mais que as seguintes; um timeout curto demais criaria falsos positivos de "timeout" logo no primeiro uso.

### Tratamento de erro (genérico, propositalmente)

`DioException.type` distingue timeout (`connectionTimeout`/`sendTimeout`/`receiveTimeout`) de erro de conexão (`connectionError`) de erro HTTP (`badResponse`, que cobre os 422/500 da E1.F1.2) — mas para esta PBI todos os casos convergem para a mesma UI genérica (mensagem + "tentar novamente"), porque diferenciar a reação é escopo da E1.F1.4. Não implementar aqui nenhum `switch` sobre `e.response?.statusCode` além do necessário para não vazar detalhe técnico na mensagem exibida.

### Fluxo de estados da tela (atualiza o da E1.F1.1)

```
idle (nenhuma foto) → preview (foto escolhida) → "Confirmar"
                                                      ↓
                                                  enviando (loading)
                                                 ↙              ↘
                                          sucesso                 erro
                                    (mostra imagem_url)    (mensagem + "tentar novamente")
                                                                  ↓
                                                            volta a "enviando"
```

"Trocar foto" (da E1.F1.1) continua disponível a partir de qualquer estado de envio — permite descartar tanto um erro quanto um sucesso e recomeçar.

## Critérios de aceite

- **Dado** que o usuário tem uma foto em preview, **quando** toca em "Confirmar", **então** um indicador de carregamento aparece e o botão fica desabilitado enquanto a requisição está em andamento.
- **Dado** que a requisição de processamento termina com sucesso, **quando** a resposta chega, **então** a imagem processada (`imagem_url`) é exibida na tela.
- **Dado** que a requisição falha por erro de rede ou timeout, **quando** isso acontece, **então** a tela mostra uma mensagem de erro clara e uma forma de tentar novamente, sem ficar presa no estado de carregamento.
- **Dado** que a requisição falha por um erro HTTP do backend (422/500 da E1.F1.2), **quando** isso acontece, **então** a tela reage da mesma forma genérica do item anterior (mensagem + tentar novamente) — não precisa (e não deve, nesta PBI) diferenciar o tipo de falha.
- **Dado** que o usuário está no estado de erro, **quando** toca em "tentar novamente", **então** a mesma foto (sem precisar escolher de novo) é reenviada.

## Riscos e pontos de atenção

- **Falso positivo de timeout no primeiro uso**: a primeira chamada ao `rembg` no backend baixa um modelo grande (~176MB, ver E1.F1.2) — se o timeout escolhido for curto demais, o app vai reportar "timeout" numa situação que na verdade é só a primeira execução sendo lenta. Testar isso considerando que a *segunda* chamada em diante é que reflete o tempo real de produção.
- **Reaproveitamento do `uploadPhotoProvider`**: como ele é `autoDispose` (a confirmar ao implementar, seguindo o padrão da E1.F1.1) ou não, decide se o estado de foto sobrevive a navegações — não é o foco desta PBI, mas vale checar que o provider de envio não fica "preso" com um estado de sucesso/erro antigo se o usuário sair da tela e voltar.
- Continua valendo o mesmo ponto de atenção da E1.F1.1 sobre `image_picker` variar entre plataformas — agora também se aplica a `readAsBytes()` no `PecaService`.
- Sem suíte de testes de integração real (nem no mobile nem no backend) — a verificação desta PBI depende de rodar a API local de verdade, igual à E1.F1.2.

## Como testar

1. Subir o backend: `docker compose up -d` (raiz do repo), depois em `backend/`: `alembic upgrade head` e `uvicorn app.main:app --reload`.
2. `flutter run -d chrome` dentro de `mobile/`, navegar até a tela de upload, escolher uma foto real.
3. **Caminho feliz**: tocar em "Confirmar", observar o indicador de carregamento, e confirmar que a imagem sem fundo aparece ao final (pode demorar bastante na primeira vez — ver "Riscos").
4. **Caminho de erro (rede/timeout)**: parar o backend (`Ctrl+C` no `uvicorn`) antes de confirmar, ou trocar temporariamente `AppConstants.apiBaseUrl` para uma porta sem nada escutando — confirmar que aparece mensagem de erro e "tentar novamente", nunca um loading infinito ou uma tela quebrada.
5. **Tentar novamente**: com o backend de volta no ar, tocar em "tentar novamente" a partir do estado de erro — confirmar que reenvia a mesma foto sem pedir pra escolher de novo.
6. `flutter analyze` e `flutter test` dentro de `mobile/`.

### Mudanças de escopo (fora do que a PBI original documentava)

1. **`errorBuilder` no `Image.network` do resultado processado** (`upload_view.dart`): não estava em "Como será feito". Descoberto ao rodar `flutter test` de verdade — o ambiente de teste do Flutter sempre recusa requisições HTTP reais (retorna 400), e sem `errorBuilder` o widget reporta um `NetworkImageLoadException` não tratado, derrubando o teste. Adicionado porque também é uma melhoria real de resiliência (se a URL processada falhar ao carregar depois do upload responder, a tela degrada para um ícone em vez de erro não tratado) — mesmo espírito da regra do projeto de nunca deixar uma chamada externa quebrar a tela sem tratamento.
