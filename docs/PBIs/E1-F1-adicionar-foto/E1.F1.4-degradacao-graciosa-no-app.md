| Feature | 1 — Adicionar peça por foto, com remoção automática de fundo |
| Estimativa | P (pequena) |
| Status | Concluída (verificação do endpoint novo só por `py_compile`, não execução real; validação manual visual no Chrome pendente) |

Ver [backlog.md](../../backlog.md) e [requisitos.md](../../requisitos.md).

## Contexto

A E1.F1.3 garante que a tela nunca trava, mas "tentar de novo" só ajuda se a falha for transitória — se o `rembg` falhar consistentemente para uma imagem, ou a rede estiver ruim por tempo indeterminado, o usuário fica num loop sem saída. Viola o requisito não-funcional do projeto: falha de IA nunca pode ser erro fatal, sempre degrada para manual.

## Descrição

Na tela de erro da E1.F1.3, oferecer "Continuar sem remoção de fundo" como alternativa a "tentar novamente".

**Para na obtenção da URL da foto original e navegação** — a tela de revisão de metadados (Feature 2) não existe ainda.

## Escopo

**Dentro do escopo:**
- Novo endpoint que aceita a foto original e devolve URL utilizável, sem depender do `rembg`/Gemini.
- Botão "Continuar sem remoção de fundo" na tela de erro, ao lado de "Tentar novamente"/"Trocar foto".
- Sucesso leva ao mesmo estado visual de "processado", com aviso diferente ("sem remoção de fundo").
- Falha desse novo caminho também tratada, sem segundo loop sem saída.

**Fora do escopo:**
- Revisão/edição de metadados — Feature 2.
- Remoção de fundo manual posterior.
- Mudança no endpoint `/processar-imagem` existente.
- Diferenciar mensagem de erro por tipo de falha (continua genérico, escopo da E1.F1.3).

**Decisão de escopo**: o backlog original citava só timeout/erro estruturado como gatilho do fallback; decidido oferecer o fallback para **qualquer** erro de envio (incluindo erro de conexão sem timeout), porque do ponto de vista do usuário os três casos significam a mesma coisa ("não consegui processar agora") e distinguir exigiria a tela conhecer `DioExceptionType`, que a E1.F1.3 não expõe fora do controller.

## Como será feito

- Novo endpoint `POST /pecas/upload-original` (multipart, mesmo formato de `/processar-imagem`): salva a imagem **sem** chamar rembg/Gemini, só grava no storage e devolve a URL. Necessário porque `PecaCreate.imagem_url` exige URL já hospedada, e hoje só existe via `/processar-imagem` ter sucesso.
- `image_service.salvar_imagem_original` (novo) delega pro `storage_adapter` já existente; rota via `run_in_threadpool`, por consistência com a E1.F1.2.
- Novo schema `ImagemOriginalResponse { imagem_url: str }`.
- Endpoint fica sem autenticação, igual ao `/processar-imagem` — inconsistência pré-existente, não corrigida aqui.
- Mobile: `EnvioSucesso` ganha campo `semRemocaoDeFundo` (default `false`); novo método `continuarSemProcessamento()` em `UploadSubmissionController`, chamando `PecaService.uploadImagemOriginal(XFile)`; se também falhar, cai no mesmo `EnvioErro` de sempre (os três botões continuam disponíveis).

**Arquivos afetados**: `app/schemas/peca.py`, `app/services/image_service.py`, `app/api/v1/pecas.py`, `peca_service.dart`, `upload_controller.dart`, `upload_view.dart`.

## Critérios de aceite

- Tela de erro mostra "Continuar sem remoção de fundo" junto com as outras duas opções.
- Sucesso desse caminho → mostra a foto original com aviso claro de que a remoção não foi aplicada.
- Resultado tem `imagem_url` válida pronta para a próxima etapa (ainda que ela não exista nesta PBI).
- Esse caminho falhando também → volta ao estado de erro genérico (três opções), sem travar.

## Riscos e pontos de atenção

- Extensão do arquivo original pode vir vazia/não reconhecível — fallback para `"jpg"` é aposta razoável, vale confirmar com upload real do Chrome.
- Dois endpoints agora sem autenticação escrevendo no disco do servidor — risco acumulado, fora do objetivo desta PBI corrigir.
- Falha em cascata (ambos os endpoints fora) deixa o usuário sem solução, mas sem travar a tela — comportamento aceito.
- A decisão de escopo (fallback para qualquer erro) é o ponto mais provável de precisar ajuste.

## Como testar

1. Subir backend e app (`flutter run -d chrome`).
2. `curl -X POST http://localhost:8000/api/v1/pecas/upload-original -F "arquivo=@foto.jpg"` → 200, imagem idêntica à original (sem transparência).
3. Pela UI: forçar falha (parar backend antes de confirmar), religar o backend, tocar "Continuar sem remoção de fundo" → imagem original + aviso correto.
4. Repetir mantendo o backend fora durante o toque → volta ao erro, três opções visíveis.
5. `flutter analyze && flutter test`.
