## Contexto

A E1.F1.3 fechou o critério de "a tela nunca trava" — qualquer falha no envio mostra uma mensagem e deixa o usuário tentar de novo. Mas "tentar de novo" só ajuda se o problema for transitório. Se o `rembg` falhar de forma consistente pra uma imagem específica (ex: formato que o modelo não processa bem), ou o usuário estiver numa rede ruim por tempo indeterminado, ele fica preso num loop de "tentar novamente" sem nenhuma saída — o cadastro nunca acontece.

Isso viola diretamente o requisito não-funcional do projeto (`requisitos.md`): "nenhuma chamada de IA pode derrubar um fluxo do usuário — falha na extração de metadados degrada para preenchimento manual, nunca para erro fatal." O texto original fala especificamente de Gemini, mas o mesmo racional já foi aplicado ao `rembg` no desenho da própria feature (ver `arquitetura.md`, "Decisões e trade-offs" sobre resiliência de IA) — é o mesmo princípio, aplicado ao ponto onde ele ainda não estava coberto.

Para a persona Marina, essa é a diferença entre "o app quebrou, desisto de cadastrar essa peça" e "tudo bem, cadastro sem o fundo bonito por enquanto e edito depois".

## Descrição

Quando o envio da foto falha (qualquer um dos casos já tratados genericamente pela E1.F1.3: timeout, erro de conexão, ou erro estruturado do backend), oferecer uma alternativa explícita ao lado de "tentar novamente": **continuar o cadastro com a foto original, sem remoção de fundo**.

**Esta PBI para na obtenção da URL da foto original e na navegação para a próxima etapa.** A tela de revisão de metadados que viria depois (Feature 2) não existe ainda — esta PBI só garante que o usuário consegue *sair* do estado de erro com uma peça utilizável, não implementa o que vem depois dela no fluxo de cadastro completo.

## Escopo

**Dentro do escopo:**
- Um novo endpoint no backend que aceita a foto original e devolve uma URL utilizável, sem depender do `rembg`/Gemini terem funcionado (ver "Como será feito" — esse endpoint não existe hoje e é o bloqueio real para esta PBI, não um detalhe de UI).
- Um botão "Continuar sem remoção de fundo" na tela de erro da E1.F1.3, ao lado de "Tentar novamente" e "Trocar foto".
- Ao tocar nesse botão, chamar o novo endpoint e, em caso de sucesso, levar a tela pro mesmo estado visual de "processado" que a E1.F1.3 já tem (reaproveitado, com um aviso diferente: "sem remoção de fundo" em vez de "fundo removido").
- Tratar também a falha *desse* novo caminho (o upload simples pode falhar pelo mesmo motivo de rede que o processamento falhou) — sem introduzir um segundo loop de erro sem saída.

**Fora do escopo (não implementar aqui):**
- A tela de revisão/edição de metadados que consome o resultado (com ou sem remoção de fundo) — Feature 2.
- Remoção de fundo manual/posterior pelo usuário (mencionada como possibilidade futura na "Descrição", não implementada agora).
- Qualquer mudança no comportamento do endpoint `POST /pecas/processar-imagem` em si — já fechado pela E1.F1.2. Esta PBI adiciona um endpoint novo, não modifica o existente.
- Diferenciar a *mensagem* de erro por tipo de falha — isso continua sendo escopo genérico da E1.F1.3 (não reabrir).

### Decisão de escopo que precisa de validação (ambiguidade real no backlog)

O critério de aceite original em `backlog.md` diz literalmente: *"Se o backend retornar o erro estruturado do E1.F1.2, **ou** a requisição expirar (timeout de rede)..."* — não menciona explicitamente erro de conexão (servidor inalcançável, sem timeout envolvido), que é um terceiro tipo de falha que a E1.F1.3 já trata (`DioExceptionType.connectionError`).

**Decisão tomada nesta PBI**: oferecer "Continuar sem remoção de fundo" para **qualquer** estado de erro da E1.F1.3, não só os dois tipos citados literalmente. Razão: do ponto de vista do usuário, os três casos (timeout, erro estruturado, sem conexão) significam a mesma coisa — "não consegui processar agora" — e o requisito não-funcional que motiva esta PBI não faz essa distinção. Restringir por tipo de erro exigiria a tela conhecer detalhes de `DioExceptionType` que a E1.F1.3 deliberadamente não expõe fora do controller, e não traz benefício real pro usuário. **Se você discordar dessa leitura, é o momento de ajustar antes do `implementar-pbi` rodar.**

## Como será feito

### Bloqueio real: não existe hoje como obter uma URL pra foto original

`PecaCreate.imagem_url` (schema usado pela Feature 2 pra criar a peça) exige uma URL já hospedada. A única forma de conseguir uma hoje é o `POST /pecas/processar-imagem` ter sucesso — que é exatamente o que falhou. Sem uma URL, não tem pra onde "continuar".

**Novo endpoint**: `POST /pecas/upload-original` (multipart, mesmo formato do `/processar-imagem`) — salva a imagem recebida **sem** chamar `rembg` nem Gemini, só grava no storage e devolve a URL. Segue a mesma camada `router → service → adapter` do resto do backend (CLAUDE.md, "Camadas do backend").

```python
# app/services/image_service.py — nova função, ao lado de processar_imagem_peca
def salvar_imagem_original(imagem_bytes: bytes, extensao: str) -> str:
    return storage_adapter.save_image(imagem_bytes, extensao=extensao)
```

```python
# app/api/v1/pecas.py — nova rota
@router.post("/upload-original", response_model=ImagemOriginalResponse)
async def upload_imagem_original(arquivo: UploadFile):
    """Salva a foto original sem processamento — usado quando
    /processar-imagem falhou e o usuário optou por continuar sem
    remoção de fundo (E1.F1.4)."""
    imagem_bytes = await arquivo.read()
    extensao = Path(arquivo.filename or "").suffix.lstrip(".") or "jpg"
    imagem_url = await run_in_threadpool(salvar_imagem_original, imagem_bytes, extensao)
    return ImagemOriginalResponse(imagem_url=imagem_url)
```

`run_in_threadpool` aqui é mais por consistência com o padrão já estabelecido na E1.F1.2 do que por necessidade real — escrever um arquivo pequeno em disco é rápido, mas evita reintroduzir o mesmo tipo de bloqueio do event loop que já foi corrigido no endpoint irmão.

Novo schema em `app/schemas/peca.py`:
```python
class ImagemOriginalResponse(BaseModel):
    imagem_url: str
```

Esse endpoint fica **sem autenticação**, igual ao `/processar-imagem` hoje (nenhum dos dois valida `usuario_id`) — inconsistência pré-existente, não introduzida nem corrigida por esta PBI.

### Mobile

Reaproveitar o `EnvioState` da E1.F1.3 em vez de criar um paralelo:

```dart
class EnvioSucesso extends EnvioState {
  const EnvioSucesso(this.imagemUrl, {this.semRemocaoDeFundo = false});
  final String imagemUrl;
  final bool semRemocaoDeFundo;
}
```

Novo método em `UploadSubmissionController`:
```dart
Future<void> continuarSemProcessamento() async {
  final foto = ref.read(uploadPhotoProvider);
  if (foto == null) return;

  state = const Enviando();
  try {
    final resultado = await ref.read(pecaServiceProvider).uploadImagemOriginal(foto);
    state = EnvioSucesso(resultado['imagem_url'] as String, semRemocaoDeFundo: true);
  } on DioException catch (e) {
    state = EnvioErro(_mensagemDeErro(e));
  } catch (_) {
    state = const EnvioErro('Não foi possível continuar. Tente novamente.');
  }
}
```

Se esse caminho também falhar, cai de volta no mesmo estado `EnvioErro` de sempre — o botão "Continuar sem remoção de fundo" continua disponível pra tentar de novo, não é um beco sem saída dentro do beco sem saída.

`PecaService` ganha `uploadImagemOriginal(XFile imagem)`, espelhando `processarImagem` mas chamando `/pecas/upload-original`.

Na UI (`_ErroEnvio`), adicionar um terceiro botão. Em `_ResultadoProcessado`, usar `semRemocaoDeFundo` pra trocar o texto:
```dart
Text(semRemocaoDeFundo
    ? 'Continuando sem remoção de fundo — você pode ajustar isso depois.'
    : 'Fundo removido! Revise os dados na próxima etapa.')
```

## Critérios de aceite

- **Dado** que o envio da foto falhou (qualquer um dos casos já cobertos pela E1.F1.3 — ver "Decisão de escopo" acima), **quando** a tela de erro aparece, **então** um botão "Continuar sem remoção de fundo" está visível, além de "Tentar novamente" e "Trocar foto".
- **Dado** que o usuário toca em "Continuar sem remoção de fundo", **quando** o upload da foto original é concluído com sucesso, **então** a tela mostra a foto original (não processada) com um aviso claro de que a remoção de fundo não foi aplicada.
- **Dado** que o usuário chegou a esse estado, **quando** ele confirma, **então** o app tem uma `imagem_url` válida pronta pra ser usada pela próxima etapa do cadastro (ainda que essa próxima etapa em si não exista nesta PBI).
- **Dado** que o upload da foto original *também* falha, **quando** isso acontece, **então** a tela volta pro estado de erro genérico (com as mesmas três opções), sem travar.

## Riscos e pontos de atenção

- **Extensão do arquivo original**: `arquivo.filename` pode vir vazio ou sem extensão reconhecível dependendo da plataforma/navegador que originou o upload — o fallback pra `"jpg"` é uma aposta razoável, mas vale confirmar com um upload feito de fato pelo Chrome (que é onde `XFile.name` vem de um blob, não de um caminho de arquivo real).
- **Endpoint sem autenticação**: mesmo padrão já existente em `/processar-imagem`, mas agora são dois endpoints publicamente abertos que escrevem no disco do servidor. Não é objetivo desta PBI corrigir isso, mas é um risco que se acumula — vale um PBI futuro de "proteger os endpoints de upload" se o projeto for além do MVP local.
- **Falha em cascata**: se o `/upload-original` falhar pelo mesmo motivo que o `/processar-imagem` falhou (ex: servidor inteiro fora do ar), o usuário fica alternando entre os dois botões sem sucesso — comportamento aceito (ainda assim não trava a tela, só não resolve o problema de fundo), não uma regressão desta PBI.
- A decisão de escopo sobre quais tipos de erro oferecem o fallback (ver seção dedicada acima) é a parte mais provável de precisar de ajuste depois de revisão.

## Como testar

1. Subir o backend (`docker compose up -d`, `alembic upgrade head`, `uvicorn app.main:app --reload`) e o app (`flutter run -d chrome`).
2. **Caminho novo endpoint isolado**: `curl -X POST http://localhost:8000/api/v1/pecas/upload-original -F "arquivo=@caminho/para/foto.jpg"` — conferir 200 e que a imagem salva em `/uploads/<...>` é idêntica à original (sem transparência).
3. **Caminho de fallback pela UI**: escolher uma foto, tocar "Confirmar", forçar uma falha (parar o backend antes de confirmar, como já feito pra validar a E1.F1.3), tocar "Continuar sem remoção de fundo" — subir o backend de volta antes desse toque (senão o fallback também falha, o que é o próximo teste) e confirmar que a imagem original aparece com o aviso correto.
4. **Fallback também falhando**: repetir o passo 3 mas manter o backend fora do ar durante o toque em "Continuar sem remoção de fundo" — confirmar que volta pro estado de erro, com as três opções ainda visíveis.
5. `flutter analyze` e `flutter test` dentro de `mobile/`.
