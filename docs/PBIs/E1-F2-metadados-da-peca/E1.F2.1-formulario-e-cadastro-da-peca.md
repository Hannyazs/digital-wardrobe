## Contexto

A Feature 1 termina com uma `imagem_url` em mãos, mas a tela de resultado (`_ResultadoProcessado`, em `upload_view.dart`) não leva a lugar nenhum. O endpoint `POST /pecas` já existe e funciona, mas nenhuma tela o chama ainda — esta PBI fecha esse elo, persistindo a peça de fato no armário.

## Descrição

Novo `PecaFormView` que: recebe a `imagemUrl` e mostra a imagem no topo; permite preencher categoria (obrigatória), subcategoria, cor principal, estação e ocasião (opcionais, espelhando `PecaCreate`); ao confirmar, chama `POST /pecas` tratando carregamento/sucesso/erro; em sucesso, volta para `WardrobeView`.

Não cobre: edição/exclusão de peça, campos tamanho/data de compra/frequência de uso (schema não tem essas colunas), nem pré-preenchimento automático (Épico 5/Gemini).

## Escopo

**Dentro:**
- `PecaFormView` com campos categoria, subcategoria, cor principal, estação, ocasião.
- Dropdown fixo só para **categoria** e **ocasião** (únicos campos com valores enumerados em `requisitos.md`); os demais ficam em `TextFormField` livre (sem lista fechada documentada em nenhum lugar do projeto).
- Validação mínima: categoria obrigatória (reflete `PecaBase.categoria: str` sem default); demais aceitam vazio.
- Ajuste de `PecaService.criarPeca` para não exigir um `Peca` completo (que requer `id`, inexistente antes da criação).
- Estados de carregamento/sucesso/erro, reaproveitando o padrão `EnvioState` já usado em `upload_controller.dart`.
- Botão "Continuar" em `_ResultadoProcessado` navegando para `PecaFormView`.
- Mecanismo de auth **só para dev** (token de teste), já que `POST /pecas` exige JWT e o app não envia nenhum hoje — ver "Ponto de atenção crítico".

**Fora de escopo:** login real via Supabase; sugestão automática via Gemini; edição/exclusão de peça; campos tamanho/data de compra/frequência de uso; listagem do armário em si.

## Como será feito

**Novos arquivos**, dentro de `views/upload/` (continuação do mesmo fluxo, mesmo padrão de `upload_controller.dart`):
- `peca_form_view.dart`, `peca_form_controller.dart` (Riverpod `Notifier<EnvioState>`).
- `core/state/envio_state.dart` — move `EnvioState` (hoje presa em `upload_controller.dart`) para um local compartilhado entre os dois controllers.
- Campos do formulário (`TextEditingController`s + 2 dropdowns) podem ficar em estado local do widget (`StatefulWidget`).

**Navegação:** `PecaFormView` recebe `imagemUrl` via construtor, chamado a partir de um novo botão "Continuar" em `_ResultadoProcessado`.

**`PecaService.criarPeca`** troca a assinatura de `criarPeca(Peca peca)` para receber os campos nomeados que `PecaCreate` espera (`imagemUrl`, `categoria`, `subcategoria?`, `corPrincipal?`, `estacao?`, `ocasiao?`), evitando construir um `Peca` fake sem `id`. Resposta continua desserializada com `Peca.fromJson`.

**Ponto de atenção crítico — auth:** `criar_peca` exige JWT (`Depends(get_current_user_id)`), diferente das rotas de upload/processamento que não exigem. `ApiClient` hoje só tem um TODO vazio para o header `Authorization` — sem ajuste, todo envio falha com 401. Login real (Supabase) é esforço grande sem PBI própria ainda; a solução aqui é o mesmo token de dev que o projeto já usa pro backend (`backend/scripts/gerar_token_teste.py`), lido via `--dart-define=DEV_AUTH_TOKEN` no interceptor do `ApiClient`. É workaround só de desenvolvimento, documentado como tal, a ser substituído quando a auth real existir.

**Arquivos afetados:** `peca_form_view.dart`, `peca_form_controller.dart`, `core/state/envio_state.dart` (novos); `upload_controller.dart` (remove `EnvioState`, passa a importar); `upload_view.dart` (botão "Continuar"); `peca_service.dart` (assinatura de `criarPeca`); `api_client.dart` (injeta `DEV_AUTH_TOKEN`).

## Critérios de aceite

- Na tela de resultado, tocar "Continuar" abre o formulário com a imagem resultante visível.
- Confirmar sem categoria preenchida impede o envio e sinaliza o campo, sem chamar a API.
- Confirmar com categoria preenchida mostra carregamento, chama `POST /pecas`, e em sucesso volta ao armário.
- Falha no envio (rede, 401, 422/500) mostra erro claro e mantém os dados preenchidos para nova tentativa.
- Após sucesso, não é possível reenviar a mesma peça voltando pelo navegador (pilha de navegação substituída, não empilhada).

## Riscos e pontos de atenção

- Falta de auth real é risco maior que esta PBI isolada — `DEV_AUTH_TOKEN` destrava dev/teste, mas alguém precisa priorizar login real antes do Épico 1 estar pronto pra usuário de verdade.
- Listas fechadas de categoria/ocasião são suposição baseada nos exemplos de `requisitos.md`; não há enum no banco, então é só UX, revisável sem migração.
- `subcategoria`/`cor_principal`/`estacao` ficam como texto livre deliberadamente — não há vocabulário de produto documentado para inventar um enum.
- Mover `EnvioState` toca código já testado (E1.F1.3/E1.F1.4) — rodar a suíte existente, não só os testes novos.

## Como testar

1. Backend local rodando + migrações aplicadas; gerar token: `cd backend && python scripts/gerar_token_teste.py`.
2. `cd mobile && flutter run -d chrome --web-port=8080 --dart-define=DEV_AUTH_TOKEN=<token>`.
3. Fluxo completo: foto → processamento → "Continuar" → formulário.
4. Confirmar vazio → validação impede envio.
5. Preencher categoria e confirmar → carregamento e retorno ao armário.
6. Checar no banco: `docker exec -it guarda-roupa-db psql -U guarda_roupa -d guarda_roupa -c "SELECT categoria, subcategoria, cor_principal, estacao, ocasiao, imagem_url FROM pecas ORDER BY criado_em DESC LIMIT 1;"`.
7. Derrubar o backend e repetir envio → erro de rede claro, dados preservados.
8. Repetir sem `DEV_AUTH_TOKEN` ou com token inválido → erro 401 tratado como erro comum, sem crash.

**Mudança de escopo não planejada — bug real encontrado e corrigido:** o formulário usava `ListView(children: [...])` para o conteúdo. `ListView` constrói os filhos lazily (via Sliver), então o botão "Salvar peça" (último filho, fora da viewport de teste de 600px) nunca chegava a ser montado na árvore de widgets — um bug real que também afetaria o app de verdade em telas pequenas (o botão simplesmente não seria alcançável até rolar, mas a lista não tinha indicação visual de scroll e o botão ficava fora do viewport inicial). Troquei por `Form > SingleChildScrollView > Column`, que constrói todo o conteúdo imediatamente (apropriado para um formulário curto) e ainda permite rolar em telas pequenas. Encontrado e corrigido durante a escrita dos testes, não fazia parte do "Como será feito" original.

**Verificação realizada (comandos reais, resultado literal):**
- `dart analyze` dentro de `mobile/`: **"No issues found!"** — usei `dart analyze` em vez de `flutter analyze` porque este último trava com uma `FormatException` no analysis server (LSP) nesta máquina, uma falha de ambiente pré-existente (relacionada ao caminho do projeto conter caracteres acentuados — "Área de Trabalho"), não ao código desta PBI. `dart analyze` usa o mesmo `analysis_options.yaml`/`flutter_lints` e não depende do analysis server, então cobre o mesmo lint set.
- `flutter test` da suíte pré-existente (`widget_test.dart`): **7/7 passando**, incluindo o teste novo de navegação via "Continuar".
- `flutter test test/peca_form_test.dart`: **0/3 passando.** Depois de corrigir o bug do `ListView` (botão agora é alcançável), os 3 testes ainda falham por dois problemas do próprio teste, não da implementação: (1) o botão fica fora da viewport padrão de 600px do `WidgetTester` e precisa de `tester.ensureVisible()` antes do `tap()`; (2) no teste de erro, o `SnackBar` tem duração própria e `pumpAndSettle()` espera essa duração terminar, então o snackbar já desapareceu quando o `expect` roda. Ambos são ajustes mecânicos de teste conhecidos (não exigem mudança no código do app) mas não foram corrigidos nesta sessão — a sessão foi interrompida a pedido do usuário depois de várias iterações de debug. **Deixado pendente, não marcado como concluído.**
