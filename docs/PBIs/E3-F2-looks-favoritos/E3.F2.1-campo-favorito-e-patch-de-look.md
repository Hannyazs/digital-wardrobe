## Contexto

Um look salvo hoje não carrega nenhum atributo além do nome. Favoritar exige uma coluna nova e uma rota que altere um look já existente — rota que ainda não existe. Esta PBI entrega só o lado backend, para a E3.F2.2 consumir.

## Descrição

- Coluna `favorito` (booleano, padrão `false`) em `looks`, com migração `0003`.
- `LookRead` passa a expor `favorito`.
- `PATCH /looks/{look_id}` com `LookUpdate`, escopado por `usuario_id`, aceitando atualização parcial. Hoje só `favorito`; a E3.F3.1 acrescenta `ocasiao` ao mesmo schema e à mesma rota.

Para aqui: nenhuma UI (E3.F2.2) e nenhum campo de ocasião (E3.F3.1).

## Escopo

**Dentro:**
- `Look.favorito: Mapped[bool]` com `server_default=false`, para os looks já existentes ficarem `false`.
- Migração `0003_look_favorito.py` (`down_revision = "0002"`).
- `LookUpdate(favorito: bool | None = None)` em `schemas/look.py`.
- `PATCH /looks/{look_id}`: 404 se o look não existe **ou** é de outro usuário; aplica só os campos enviados (`model_dump(exclude_unset=True)`).

**Fora:**
- Ocasião (E3.F3.1), registro de uso (E3.F4.1), edição do nome ou das peças do look, exclusão de look.
- Qualquer chamada do app (E3.F2.2).

## Como será feito

- **`app/db/models.py`**: `favorito: Mapped[bool] = mapped_column(Boolean, nullable=False, server_default=expression.false())` em `Look`.
- **`alembic/versions/0003_look_favorito.py`**: `op.add_column("looks", sa.Column("favorito", sa.Boolean(), nullable=False, server_default=sa.false()))`; o `downgrade` faz `drop_column`.
- **`app/schemas/look.py`**: `favorito: bool` em `LookRead`; `LookUpdate` novo.
- **`app/api/v1/looks.py`**: `atualizar_look` filtra por `Look.id == look_id AND Look.usuario_id == usuario_id` com `selectinload(Look.pecas)`. Faz `setattr` nos campos enviados, `commit()` e devolve uma consulta nova, não `refresh()`. Motivo: o `refresh()` invalidaria `pecas` e causaria o mesmo `MissingGreenlet` já corrigido na E3.F1.1.
- Usar `PATCH` em vez de `PUT` porque o look é atualizado por campos isolados. `pecas.py` usa `PUT` porque o formulário de peça reenvia tudo.

## Critérios de aceite

- Dado um look do usuário, quando `PATCH /looks/{id}` envia `{"favorito": true}`, então a resposta traz `favorito: true` e `GET /looks` reflete a mudança.
- Dado um look recém-criado, então `favorito` é `false` por padrão.
- Dado um `look_id` inexistente ou de outro usuário, quando `PATCH` é chamado, então a API responde 404 e nada muda no banco.
- Dado um corpo `{}`, então a API responde 200 sem alterar nada.
- Dado um look anterior à migração, então `GET /looks` o devolve com `favorito: false`.

## Definição de pronto

- [x] `alembic upgrade head` aplica a `0003` num Postgres com `0002` já aplicada; `alembic downgrade -1` também funciona.
- [x] Critérios de aceite verificados com a API real (`uvicorn` + `curl`, dois usuários), como na E3.F1.1 — o projeto ainda não tem `pytest` (E1.F1.5), então não há teste automatizado novo.
- [x] `POST /looks` e `GET /looks` continuam funcionando sem mudança de contrato além do campo novo na resposta.
- [x] Status deste arquivo e do `backlog.md` atualizado ao final.

## Riscos e pontos de atenção

- Reaproveitar a mesma rota `PATCH` para `ocasiao` (E3.F3.1) só funciona se o schema distinguir "campo ausente" de "campo `null`". Por isso `exclude_unset`, e não `if valor is not None`.
- Mesmo risco de `MissingGreenlet` já visto na E3.F1.1: não usar `refresh()` na resposta.

## Como testar

1. Backend local rodando (`docker compose up -d`, `alembic upgrade head`, `uvicorn app.main:app --reload`).
2. `cd backend && python scripts/gerar_token_teste.py` e criar um look (`POST /looks`) com o token.
3. Conferir que `favorito` vem `false` na resposta do `POST` e no `GET /looks`.
4. `PATCH /looks/{id}` com `{"favorito": true}` → 200 e `favorito: true`; `GET /looks` confirma.
5. `PATCH` com um UUID aleatório → 404.
6. Repetir o `PATCH` com o token de um segundo usuário sobre o look do primeiro → 404, e o `favorito` segue `true` para o dono.
7. `docker exec -it guarda-roupa-db psql -U guarda_roupa -d guarda_roupa -c "SELECT nome, favorito FROM looks;"`.

## Log de implementação

**Entregue:**
- `backend/app/db/models.py` — `Look.favorito` (`Boolean`, `nullable=False`, `server_default=expression.false()`).
- `backend/alembic/versions/0003_look_favorito.py` (nova) — `add_column` com `server_default` falso; `downgrade` faz `drop_column`.
- `backend/app/schemas/look.py` — `favorito: bool` em `LookRead`; `LookUpdate(favorito: bool | None = None)`.
- `backend/app/api/v1/looks.py` — `PATCH /looks/{look_id}` (`atualizar_look`): busca por `id` + `usuario_id` (404 para inexistente e para look de outro usuário), aplica `model_dump(exclude_unset=True)`, `commit()` e responde com consulta nova com `selectinload(Look.pecas)`.

**Mudança em relação ao "Como será feito":**
- `{"favorito": null}` explícito é rejeitado com 422 por um `field_validator` em `LookUpdate`. A PBI não previa esse caso, e como a coluna é `NOT NULL` o resultado seria erro de banco (500). A validação fica no schema e não no router, para não impedir que campos anuláveis futuros (`ocasiao`, E3.F3.1) sejam limpos com `null`.
- A resposta do `PATCH` usa `populate_existing=True` na consulta nova: a instância já está na sessão, e sem isso a consulta poderia devolver o estado em cache em vez do recém-gravado.

**Verificação realizada (execução real):**
- Docker Desktop estava parado nesta sessão; foi iniciado, e o container `guarda-roupa-db` (já existente, com dados de dev) subiu com `pg_isready` OK. Banco estava na revisão `0002`.
- Look inserido por SQL antes da migração; `alembic upgrade head` → `Running upgrade 0002 -> 0003`; `SELECT nome, favorito FROM looks` → todos `f`, inclusive o look anterior à migração.
- `alembic downgrade -1` → coluna `favorito` removida (colunas restantes: `id usuario_id criado_em nome`); `alembic upgrade head` de novo → `0003 (head)`.
- API real (`uvicorn` + `curl`, usuários A e B com tokens de `gerar_token_teste.py`):
  - `POST /looks` → 201 com `"favorito":false`.
  - `PATCH {"favorito":true}` → 200 com `"favorito":true`; `GET /looks` do usuário A reflete `true` e não traz os looks de outros usuários.
  - `PATCH {}` → 200, `favorito` inalterado (`true`).
  - `PATCH {"favorito":null}` → 422 (`favorito não pode ser nulo.`).
  - `PATCH` com UUID inexistente → 404 `Look não encontrado.`
  - `PATCH` com o token do usuário B sobre o look de A → 404; `psql` confirma `favorito = t` para o dono.
  - `PATCH {"favorito":false}` → 200 `false`.
- `python -m compileall app alembic` sem erros.
- Dados de teste (2 looks e 1 peça criados por esta verificação) removidos do banco depois; os 3 looks pré-existentes ficaram intactos.

**Pendente / observações:**
- Sem teste automatizado: o projeto ainda não tem `pytest` (E1.F1.5), então a verificação foi manual e não é repetível por suíte.
- O app (`mobile/`) não foi tocado; o campo `favorito` extra na resposta não quebra o `Look.fromJson` atual, que ignora chaves desconhecidas — não executei `flutter test` nesta PBI por isso.
