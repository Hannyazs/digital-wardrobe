## Contexto

Organizar looks por ocasião (trabalho, faculdade, festa, academia, viagem) exige que o look carregue essa informação. Hoje só `Peca` tem `ocasiao`. Esta PBI dá a base de dados e de API; as telas ficam para as E3.F3.2 e E3.F3.3.

## Descrição

- Coluna `ocasiao` (texto, opcional) em `looks`, com migração `0005`.
- `LookRead` expõe `ocasiao`; `LookCreate` e `LookUpdate` a aceitam.
- A ocasião pode ser trocada ou removida depois, pelo `PATCH` da E3.F2.1.

Para aqui: nenhuma UI (E3.F3.2 e E3.F3.3), nenhum filtro no servidor.

## Escopo

**Dentro:**
- `Look.ocasiao: Mapped[str | None]`, nullable, sem enum no banco. É o mesmo critério de `Peca.ocasiao`, documentado em `peca_opcoes.dart`: a lista fixa é só UX.
- Migração `0005_look_ocasiao.py` (`down_revision = "0004"`).
- `ocasiao: str | None = None` em `LookCreate` e `LookUpdate`. Um validador normaliza string vazia ou só com espaços para `None`.
- `criar_look` grava `ocasiao`; `atualizar_look` já aplica campos via `exclude_unset`, então `{"ocasiao": null}` limpa o campo.

**Fora:**
- Validar `ocasiao` contra a lista fixa no servidor (`Peca` também não valida).
- Filtro por ocasião no `GET /looks`: a lista completa já vem sem paginação, e o filtro é client-side (E3.F3.3), como na E2.F2.1.
- Ocasião múltipla por look.

## Como será feito

- **`app/db/models.py`**: `ocasiao: Mapped[str | None] = mapped_column(String, nullable=True)` em `Look`.
- **`alembic/versions/0005_look_ocasiao.py`**: `add_column` nullable; `downgrade` com `drop_column`.
- **`app/schemas/look.py`**: campo nos três schemas, mais `field_validator("ocasiao")` compartilhado por `LookCreate` e `LookUpdate`.
- **`app/api/v1/looks.py`**: `criar_look` passa `ocasiao=dados.ocasiao` ao construtor de `Look`. `atualizar_look` não muda.

## Critérios de aceite

- Dado `POST /looks` com `ocasiao: "Trabalho"`, então a resposta e o `GET /looks` trazem `ocasiao: "Trabalho"`.
- Dado `POST /looks` sem `ocasiao`, então o look é criado com `ocasiao: null`.
- Dado `PATCH /looks/{id}` com `{"ocasiao": "Festa"}`, então a ocasião muda e `favorito` não é alterado.
- Dado `PATCH` com `{"ocasiao": null}` ou `{"ocasiao": "  "}`, então a ocasião é removida (`null`).
- Dado `PATCH` com `{"favorito": true}` sem `ocasiao`, então a ocasião existente é preservada.
- Dado um look de outro usuário, então `PATCH` responde 404.

- [x] Critérios de aceite verificados com a API real (`uvicorn` + `curl`, dois usuários).
- [x] Looks criados antes da migração aparecem com `ocasiao: null`.
- [x] Status deste arquivo e do `backlog.md` atualizado ao final.

## Riscos e pontos de atenção

- O ponto sensível é distinguir "ausente" de `null` no `PATCH`: se alguém trocar `exclude_unset` por `exclude_none`, limpar a ocasião deixa de funcionar. Os critérios de aceite 4 e 5 cobrem isso.
- Texto livre no banco permite capitalização diferente ("trabalho" e "Trabalho"). O app só envia valores de `ocasioesFixas`, então o risco é baixo, mas filtros devem comparar o valor exato.

## Como testar

1. Backend com a `0005` aplicada; gerar token com `python scripts/gerar_token_teste.py`.
2. `POST /looks` com `ocasiao: "Trabalho"` → 201 com `ocasiao` preenchida; repetir sem o campo → `null`.
3. `PATCH {"ocasiao": "Festa"}` → ocasião muda.
4. `PATCH {"favorito": true}` → ocasião segue `"Festa"`.
5. `PATCH {"ocasiao": null}` → ocasião vira `null`.
6. `PATCH` com o token de outro usuário → 404.
7. `psql`: `SELECT nome, ocasiao, favorito FROM looks;`.

## Mudança de escopo: várias ocasiões por look (2026-10-20)

O usuário pediu que um look possa ter **várias** ocasiões (hoje só dava para escolher uma). A PBI original (ocasião única, texto) foi mantida acima como registro; o estado atual é:

- **Banco:** `looks.ocasiao` (texto) virou `looks.ocasioes` (`ARRAY(String)`, `NOT NULL`, padrão `{}`) pela migração `backend/alembic/versions/0008_look_ocasioes.py`, no mesmo padrão da `0004` (peças). As ocasiões já salvas são preservadas (`'Trabalho'` → `{Trabalho}`); `NULL` e texto vazio viram `{}`. O `downgrade` volta para uma ocasião só (guarda a primeira de cada look).
- **API:** `LookCreate.ocasioes` (lista, padrão `[]`), `LookUpdate.ocasioes` e `LookRead.ocasioes`. Itens são normalizados (`strip`, sem vazios nem repetidos, ordem mantida). Limpar = `{"ocasioes": []}`; `null` explícito agora é **422** (a coluna é `NOT NULL`, como `favorito`). A chave antiga `ocasiao` deixou de existir (o app é o único cliente e foi atualizado junto; se enviada, é ignorada).
- **Critérios de aceite** reinterpretados para lista: `POST` grava e devolve a lista; sem o campo, `[]`; `PATCH` troca a lista inteira; `PATCH` só com `favorito` preserva as ocasiões; look de outro usuário → 404.

**Verificação realizada (execução real):**
- Migração com dados reais: antes, 8 looks com `Casual`, `Trabalho`, `Faculdade`, `Festa` e vazios, mais 3 de teste (`Trabalho`, `NULL`, `''`). Depois do `upgrade`: `{Casual}`, `{Trabalho}`, `{Faculdade}`, `{Festa}` e `{}` nos demais; `downgrade -1` devolveu os mesmos valores únicos; `upgrade head` de novo → `0008 (head)`. Os looks de teste foram removidos e os 8 reais ficaram intactos.
- API (`uvicorn` na porta 8765, `curl`, usuários A e B): `POST` com `["Trabalho","Faculdade"," Trabalho ",""]` → `["Trabalho","Faculdade"]`; `POST` sem campo → `[]`; `PATCH {"ocasioes":["Festa","Casual"]}` → troca, `favorito` intacto; `PATCH {"favorito":true}` → ocasiões preservadas; `PATCH {"ocasioes":[]}` e `["  ",""]` → `[]`; `{"ocasioes":null}` e `{"favorito":null}` → 422; `{"ocasiao":"Praia"}` → 200 sem gravar; outro usuário → 404.
- `python -m compileall -q app alembic` sem erros.
