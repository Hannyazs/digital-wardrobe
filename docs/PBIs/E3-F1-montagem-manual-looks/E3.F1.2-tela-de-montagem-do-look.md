## Contexto

A E3.F1.1 deixou `POST /looks` pronto, mas nada no app o chama ainda — a tela "Looks" (`looks_view.dart`) é só um placeholder. Esta PBI fecha a história "quero montar um look escolhendo peças do meu armário, para salvar combinações que eu já sei que funcionam", do lado do app.

## Descrição

Nova `MontarLookView`: usuário seleciona peças do próprio armário (reaproveitando os dados já buscados por `pecaListProvider`), dá um nome ao look, confirma, e o app chama `POST /looks`. Acessível por um botão novo na `LooksView` (hoje só tem um texto fixo). Termina aqui: não mostra os looks salvos depois (isso é a E3.F1.3) — ao salvar com sucesso, só volta para `LooksView` com uma confirmação.

## Escopo

**Dentro do escopo:**
- Botão/FAB em `LooksView` navegando para `MontarLookView` (mesmo padrão do FAB "Adicionar peça" em `WardrobeView` → `UploadView`).
- Grade de peças do armário, agrupada por categoria (reaproveita `agruparPorCategoria`), cada miniatura alternando selecionada/não ao toque.
- Campo de nome do look (obrigatório, espelha `LookCreate.nome: str` sem default).
- Validação: nome preenchido **e** pelo menos 1 peça selecionada antes de habilitar "Salvar look".
- Estados de carregamento/sucesso/erro no envio; em sucesso, volta para `LooksView` com um `SnackBar` de confirmação.
- Armário vazio (nenhuma peça cadastrada): mensagem orientando a cadastrar uma peça primeiro, sem deixar abrir uma tela de seleção vazia.

**Fora de escopo:**
- Exibir a lista de looks já salvos (E3.F1.3) — `LooksView` continua sem listagem própria após esta PBI.
- Favoritar o look, associar ocasião, excluir/editar um look salvo (Features 2/3 do Épico 3, cada uma com sua quebra quando chegar a vez).
- Reordenar as peças selecionadas dentro do look (a associação `looks_pecas` não guarda posição — ver E3.F1.1, "Riscos").
- Filtro por cor/estação/ocasião na grade de seleção (poderia reaproveitar a E2.F2.1 depois, mas não é pedido nesta história).

## Como será feito

- **`mobile/lib/models/look.dart`** (novo): `Look` espelhando `LookRead` (`id`, `nome`, `criadoEm`, `pecas: List<Peca>`), com `fromJson`.
- **`mobile/lib/services/look_service.dart`** (novo): `LookService.criarLook({required String nome, required List<String> pecaIds})` → `POST /looks` com `{"nome": ..., "peca_ids": [...]}`, retorna `Look.fromJson`. Mesmo padrão de `PecaService` (usa `ApiClient.instance`, já injeta `DEV_AUTH_TOKEN`).
- **`mobile/lib/views/looks/montar_look_controller.dart`** (novo):
  - `selecaoLookProvider` (`StateProvider.autoDispose<Set<String>>`, ids de peça selecionados).
  - `MontagemLookState` (sealed: `Idle`/`Enviando`/`Sucesso`/`Erro`) — **não** reaproveita `EnvioState` (`core/state/envio_state.dart`): esse estado carrega um `imagemUrl` obrigatório no caso de sucesso, que não existe aqui (um look não é uma imagem única); forçar um valor fake seria pior que um sealed class próprio e pequeno.
  - `MontagemLookController extends Notifier<MontagemLookState>` com `salvar({required String nome, required Set<String> pecaIds})`, mapeando erros Dio como em `PecaFormController._mensagemDeErro`.
- **`mobile/lib/views/looks/montar_look_view.dart`** (novo): consome `pecaListProvider` (de `wardrobe_controller.dart`) para a grade; `Form` com `TextFormField` pro nome; grade reaproveitando `agruparPorCategoria`, cada item com um overlay de seleção (`Checkbox`/ícone de check sobre a miniatura); botão "Salvar look" fixo, desabilitado até nome + seleção válidos.
- **`mobile/lib/views/looks/looks_view.dart`**: vira `ConsumerWidget`/mantém `StatelessWidget` e ganha um `FloatingActionButton` ("Montar look") navegando para `MontarLookView`; texto placeholder atual é removido só quando a E3.F1.3 trouxer a listagem real — por ora, mantém o texto mas acrescenta o botão.
- **Arquivos afetados**: `models/look.dart`, `services/look_service.dart`, `views/looks/montar_look_controller.dart`, `views/looks/montar_look_view.dart` (novos); `views/looks/looks_view.dart` (FAB novo).

## Critérios de aceite

- Dado o armário com peças cadastradas, quando o usuário abre "Looks" e toca em "Montar look", então vê a grade de peças agrupada por categoria, com um campo de nome.
- Dado que nenhuma peça foi selecionada ou o nome está vazio, quando o usuário tenta salvar, então o botão permanece desabilitado (não chama a API).
- Dado nome preenchido e 1+ peças selecionadas, quando o usuário confirma, então `POST /looks` é chamado e, em sucesso, o app volta para "Looks" com uma confirmação visível.
- Dado uma falha no envio (rede, 401, 422), quando ela ocorre, então uma mensagem clara aparece e a seleção/nome permanecem preenchidos para nova tentativa.
- Dado um armário sem nenhuma peça cadastrada, quando o usuário toca em "Montar look", então vê uma orientação para cadastrar uma peça primeiro, sem abrir uma grade vazia.

## Riscos e pontos de atenção

- `pecaListProvider` já existe e é `autoDispose` — reaproveitá-lo aqui busca o armário de novo ao entrar na tela (sem cache entre telas), aceitável no tamanho atual do armário do MVP.
- Nome do look é texto livre sem limite de tamanho documentado — mesmo tratamento dado a `subcategoria`/`cor_principal` em `Peca` (sem vocabulário fechado para inventar).
- Igual à E1.F2.1: `POST /looks` exige JWT; o fluxo só funciona com `DEV_AUTH_TOKEN` configurado até existir login real via Supabase.

## Como testar

1. Backend local rodando + migrações aplicadas (`0002` incluída); gerar token: `cd backend && python scripts/gerar_token_teste.py`.
2. Cadastrar 2+ peças pelo fluxo normal do app (ou via `POST /pecas` direto).
3. `cd mobile && flutter run -d chrome --web-port=8080 --dart-define=DEV_AUTH_TOKEN=<token>`.
4. Abrir "Looks" → "Montar look" → selecionar peças, preencher nome, salvar → conferir volta para "Looks" com confirmação.
5. Tentar salvar sem nome ou sem peça selecionada → botão permanece desabilitado.
6. Derrubar o backend e tentar salvar → erro de rede claro, dados preservados.
7. Com um usuário sem nenhuma peça cadastrada, abrir "Montar look" → conferir orientação para cadastrar peça, sem grade vazia.
