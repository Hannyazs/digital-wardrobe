## Contexto

Com login real, a configuração do backend precisa deixar de ser "de desenvolvimento": origens permitidas, segredos e a chave de serviço do Supabase.

## Descrição

- CORS restrito às origens do app (hoje vem de `cors_origins_list`).
- Segredos (`SUPABASE_JWT_SECRET` se ainda usado, `SUPABASE_SERVICE_KEY`) apenas em variáveis de ambiente, nunca no repositório nem em logs.
- A chave de serviço existe só no backend; o app usa apenas a chave pública.
- O script `gerar_token_teste.py` fica documentado como ferramenta apenas de desenvolvimento.

Para aqui: não inclui RLS (o PostgreSQL continua fora do Supabase).

## Escopo

**Dentro:** revisão de `config.py`, `.env.example`, `README.md` e `.gitignore`; checklist de configuração para produção.

**Fora de escopo:** migração do PostgreSQL; CI; rotação automática de segredos.

## Como será feito

- Revisar quais variáveis têm valor padrão perigoso (por exemplo, origens `*`) e exigir valor explícito fora do desenvolvimento.
- Conferir que nenhum log imprime tokens ou chaves.
- Conferir que `.env` e arquivos de token seguem no `.gitignore`.
- Arquivos: `app/core/config.py`, `.env.example`, `README.md`.

## Critérios de aceite

- Dada a configuração de produção, então CORS aceita apenas as origens do app.
- Dado o repositório, então não contém segredos nem chave de serviço.
- Dado o app, então não contém a chave de serviço.
- O README descreve o que é só de desenvolvimento e o que é de produção.

## Como testar

1. Subir a API com a configuração de produção de exemplo e chamar de uma origem permitida e de outra não permitida.
2. Buscar segredos no repositório e nos logs.
