## Contexto

O interceptor do `ApiClient` injeta o `DEV_AUTH_TOKEN` fixo. Com sessão real, ele deve usar o `access_token` do usuário logado e tratar a expiração.

## Descrição

- O interceptor envia o `access_token` da sessão atual.
- O token é renovado antes de expirar (a sessão do Supabase já oferece renovação).
- Resposta 401 que persiste após a renovação leva ao login, com aviso claro.
- `DEV_AUTH_TOKEN` é removido do app e do README.

Para aqui: não muda o backend (E9.F1.1 já aceita os tokens).

## Escopo

**Dentro:** `ApiClient`, tratamento global de 401, remoção do token de desenvolvimento no app e na documentação do app.

**Fora de escopo:** telas de auth (E9.F2.1); o script `gerar_token_teste.py` do backend (continua só para testes de desenvolvimento).

## Como será feito

- O interceptor lê a sessão atual a cada requisição; no 401, tenta uma renovação e repete a requisição uma vez.
- Se continuar 401, encerra a sessão local e leva ao login, preservando a mensagem "sessão expirada".
- Testes com `ApiClient`/auth falsos.
- Arquivos: `core/network/api_client.dart`, `core/auth/*`, `README.md` (seção de token de desenvolvimento).

## Critérios de aceite

- Dada uma sessão válida, então as requisições vão com o token do usuário logado.
- Dado um token vencido, então ocorre uma renovação e a requisição original é repetida uma vez.
- Dada uma sessão que não renova, então o usuário volta ao login com aviso de sessão expirada.
- Dado o app sem `DEV_AUTH_TOKEN`, então tudo funciona só com a conta real.

## Riscos e pontos de atenção

- Laço de repetição em 401: a repetição é limitada a uma tentativa.
- Requisições simultâneas durante a renovação podem pedir renovação duas vezes; tratar para não derrubar a sessão.

## Como testar

1. Logar e navegar pelo app.
2. Forçar expiração (sessão curta ou token inválido) e conferir a renovação ou o retorno ao login.
3. Buscar `DEV_AUTH_TOKEN` no app e confirmar que não existe.
