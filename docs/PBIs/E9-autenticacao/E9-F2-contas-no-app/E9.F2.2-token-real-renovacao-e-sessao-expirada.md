## Contexto

O interceptor do `ApiClient` injeta o `DEV_AUTH_TOKEN` fixo. Com sessão real, ele deve usar o `access_token` do usuário logado e tratar a expiração.

## Descrição

- O interceptor envia o `access_token` da sessão atual.
- O token é renovado antes de expirar (a sessão do Supabase já oferece renovação).
- Resposta 401 que persiste após a renovação leva ao login, com aviso claro.
- `DEV_AUTH_TOKEN` é removido do app e do README.

Para aqui: não muda o backend (E9.F1.1 já aceita os tokens).

## Escopo

**Dentro:** `ApiClient`, tratamento global de 401, remoção do token de desenvolvimento no app e na documentação do app.

**Fora de escopo:** telas de auth (E9.F2.1); o script `gerar_token_teste.py` do backend (continua só para testes de desenvolvimento).

## Como será feito

- O interceptor lê a sessão atual a cada requisição; no 401, tenta uma renovação e repete a requisição uma vez.
- Se continuar 401, encerra a sessão local e leva ao login, preservando a mensagem "sessão expirada".
- Testes com `ApiClient`/auth falsos.
- Arquivos: `core/network/api_client.dart`, `core/auth/*`, `README.md` (seção de token de desenvolvimento).

## Critérios de aceite

- Dada uma sessão válida, então as requisições vão com o token do usuário logado.
- Dado um token vencido, então ocorre uma renovação e a requisição original é repetida uma vez.
- Dada uma sessão que não renova, então o usuário volta ao login com aviso de sessão expirada.
- Dado o app sem `DEV_AUTH_TOKEN`, então tudo funciona só com a conta real.

## Riscos e pontos de atenção

- Laço de repetição em 401: a repetição é limitada a uma tentativa.
- Requisições simultâneas durante a renovação podem pedir renovação duas vezes; tratar para não derrubar a sessão.

## Como testar

1. Logar e navegar pelo app.
2. Forçar expiração (sessão curta ou token inválido) e conferir a renovação ou o retorno ao login.
3. Buscar `DEV_AUTH_TOKEN` no app e confirmar que não existe.

## Log de implementação

**2026-11-07** (implementada junto com a E9.F2.3, a pedido do usuário).

### Entregue
- `lib/core/network/auth_interceptor.dart` (novo): `AuthInterceptor` do Dio.
  - Em cada requisição: `Authorization: Bearer <token da sessão>`; se a sessão já venceu, renova antes de enviar.
  - 401 com token: se outra requisição já renovou, só repete com o token atual; senão renova e repete **uma** vez (marca `auth_repetida` no `extra`, sem laço). `FormData` é clonado para a repetição (um corpo multipart já enviado não pode ser lido de novo).
  - Renovação impossível ou 401 de novo: `encerrarSessaoExpirada()` → login com "Sua sessão expirou. Entre de novo."
  - 401 sem token (sem sessão) e outros erros não mexem na sessão.
- `lib/core/network/api_client.dart`: sem `DEV_AUTH_TOKEN`; `ApiClient.usarConta(auth)` liga o interceptor (chamado no `main.dart`).
- `lib/core/auth/auth_service.dart`: `tokenDeAcesso()`, `renovarToken()` (renovações simultâneas compartilham uma só chamada ao Supabase), `encerrarSessaoExpirada()`, `EstadoDaConta`/`AvisoDaConta`. Um `signedOut` que não veio do "Sair" (ex.: o Supabase não conseguiu renovar sozinho) também vira o aviso de sessão expirada.
- `lib/views/auth/login_view.dart`: mostra o aviso de sessão expirada.
- `test/auth_interceptor_test.dart` (novo, 8 testes) com uma API falsa no adaptador do Dio; 2 testes de tela em `test/auth_test.dart`.
- `README.md`, `.claude/skills/implementar-pbi/SKILL.md`: sem `DEV_AUTH_TOKEN` para o app; o `gerar_token_teste.py` continua documentado só para chamar a API direto.

### Decisões que a PBI não detalhava
- "Renovar antes de expirar" fica com o próprio `supabase_flutter` (renovação automática); o interceptor cobre o caso em que isso não aconteceu (aba em segundo plano, sessão vencida ao reabrir).
- Requisições simultâneas: a renovação é compartilhada no `SupabaseAuthService` e o interceptor não renova de novo se o token já mudou.
