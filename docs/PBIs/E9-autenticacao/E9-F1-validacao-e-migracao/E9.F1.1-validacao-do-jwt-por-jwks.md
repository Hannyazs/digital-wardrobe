## Contexto

Hoje `get_current_user_id` valida o JWT só com HS256 e o segredo estático `SUPABASE_JWT_SECRET`. O Supabase migrou para chaves de assinatura assimétricas publicadas num endpoint JWKS, então o token de um projeto real pode não passar por essa validação. Esta PBI deixa o backend pronto para tokens reais, mantendo a regra do projeto: o `usuario_id` vem sempre do token.

## Descrição

- Validar o token com as chaves públicas do projeto (JWKS), conferindo emissor, audiência e expiração.
- Manter HS256 com o segredo apenas se a verificação do projeto real mostrar que ele ainda é necessário (transição).
- Token inválido, expirado, de outro projeto ou sem `sub` retorna 401.

Para aqui: não cria telas nem login; o app passa a enviar tokens reais na E9.F2.2.

## Escopo

**Dentro:**
- Ajuste de `app/core/security.py` e de `app/core/config.py` (URL do projeto / do JWKS).
- Testes `pytest` com tokens gerados localmente (chave válida, chave errada, expirado, sem `sub`, audiência errada).

**Fora de escopo:** criar o projeto Supabase; cadastro e login; remover o `DEV_AUTH_TOKEN` do app (E9.F2.2); migrar dados (E9.F1.2).

## Como será feito

- Buscar as chaves públicas no JWKS do projeto, com cache em memória e renovação quando surgir uma chave desconhecida; falha ao buscar o JWKS vira 401/503 claro, nunca exceção crua.
- Qual algoritmo o projeto real emite é **verificado na configuração do Supabase**, não presumido; o código aceita só o(s) algoritmo(s) confirmado(s).
- Biblioteca de JWT já usada (`jwt`); qualquer dependência nova precisa ser justificada ao implementar.
- Arquivos: `app/core/security.py`, `app/core/config.py`, `tests/test_security.py` (novo), `.env.example`.

## Critérios de aceite

- Dado um token assinado por uma chave do JWKS do projeto, quando chama um endpoint autenticado, então a requisição passa e o `usuario_id` é o `sub`.
- Dado um token expirado, de chave desconhecida, de outro emissor ou com audiência errada, então a resposta é 401.
- Dado um token sem `sub`, então a resposta é 401.
- Dado que o JWKS está inacessível, então a resposta é um erro estruturado, não um 500 sem tratamento.
- A suíte `pytest` existente continua passando.

## Riscos e pontos de atenção

- Sem o projeto Supabase criado, só dá para testar com chaves geradas localmente; a validação real fica para quando o projeto existir.
- Depender do JWKS adiciona uma chamada de rede; o cache evita uma por requisição.

## Como testar

1. `cd backend && pytest tests/test_security.py`.
2. `pytest` completo.
3. Com o projeto real configurado, chamar um endpoint autenticado com um token de login de verdade e conferir o 200.
