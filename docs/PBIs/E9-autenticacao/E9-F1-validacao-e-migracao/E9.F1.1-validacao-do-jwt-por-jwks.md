## Contexto

Hoje `get_current_user_id` valida o JWT só com HS256 e o segredo estático `SUPABASE_JWT_SECRET`. O Supabase migrou para chaves de assinatura assimétricas publicadas num endpoint JWKS, então o token de um projeto real pode não passar por essa validação. Esta PBI deixa o backend pronto para tokens reais, mantendo a regra do projeto: o `usuario_id` vem sempre do token.

## Descrição

- Validar o token com as chaves públicas do projeto (JWKS), conferindo emissor, audiência e expiração.
- Manter HS256 com o segredo apenas se a verificação do projeto real mostrar que ele ainda é necessário (transição).
- Token inválido, expirado, de outro projeto ou sem `sub` retorna 401.

Para aqui: não cria telas nem login; o app passa a enviar tokens reais na E9.F2.2.

## Escopo

**Dentro:**
- Ajuste de `app/core/security.py` e de `app/core/config.py` (URL do projeto / do JWKS).
- Testes `pytest` com tokens gerados localmente (chave válida, chave errada, expirado, sem `sub`, audiência errada).

**Fora de escopo:** criar o projeto Supabase; cadastro e login; remover o `DEV_AUTH_TOKEN` do app (E9.F2.2); migrar dados (E9.F1.2).

## Como será feito

- Buscar as chaves públicas no JWKS do projeto, com cache em memória e renovação quando surgir uma chave desconhecida; falha ao buscar o JWKS vira 401/503 claro, nunca exceção crua.
- Qual algoritmo o projeto real emite é **verificado na configuração do Supabase**, não presumido; o código aceita só o(s) algoritmo(s) confirmado(s).
- Biblioteca de JWT já usada (`jwt`); qualquer dependência nova precisa ser justificada ao implementar.
- Arquivos: `app/core/security.py`, `app/core/config.py`, `tests/test_security.py` (novo), `.env.example`.

## Critérios de aceite

- Dado um token assinado por uma chave do JWKS do projeto, quando chama um endpoint autenticado, então a requisição passa e o `usuario_id` é o `sub`.
- Dado um token expirado, de chave desconhecida, de outro emissor ou com audiência errada, então a resposta é 401.
- Dado um token sem `sub`, então a resposta é 401.
- Dado que o JWKS está inacessível, então a resposta é um erro estruturado, não um 500 sem tratamento.
- A suíte `pytest` existente continua passando.

### Evidência do algoritmo (projeto real)
`GET https://vxzadsokzxwqalqvnepd.supabase.co/auth/v1/.well-known/jwks.json` em 2026-11-07 devolveu uma única chave: `kid 1224cc13-d075-4365-9ca5-e61abdd7f841`, `kty EC`, `crv P-256`, `alg ES256`. Por isso o código aceita **só ES256** para tokens do Supabase. Não há segredo HS256 do projeto em uso.

### Decisões que a PBI não detalhava
- **Token de desenvolvimento mantido (transição).** A PBI previa manter HS256 "só se o projeto real precisar"; o projeto não precisa. Mas sem ele o app pararia de funcionar até a E9.F2.2 (ele ainda usa `DEV_AUTH_TOKEN`). Ficou aceito **apenas se `SUPABASE_JWT_SECRET` estiver preenchido**; em produção ele fica vazio. Exigir isso fora do desenvolvimento é da E9.F3.2.
- **Seleção por `alg` sem confusão de algoritmo:** o `alg` do cabeçalho só escolhe o caminho; cada caminho passa uma lista fixa a `jwt.decode`, e o caminho HS256 usa só o segredo, nunca a chave pública (coberto por teste).
- **Nenhuma dependência nova:** `PyJWKClient` e `cryptography` já vêm de `pyjwt[crypto]` (PyJWT 2.15.1 instalado). O próprio PyJWT espera 30 s entre buscas forçadas por `kid` novo (`cooldown_duration`), o que limita quem tentar forçar buscas com `kid` aleatório.
- **503 para JWKS inacessível** (a PBI aceitava 401 ou 503): é falha do servidor, não do token, e o app não deve mandar o usuário para o login por causa disso.
- Ajuste de testes: `pytest` não estava instalado na venv recém-criada; rodado `pip install -r requirements-dev.txt` (ambiente, não código).

### Verificação
- `pytest tests/test_security.py` → `25 passed`.
- `pytest` (suíte inteira, Postgres do `docker compose` no ar) → `351 passed` (326 anteriores + 25 novos).

### Pendente

### Correção pós-entrega (2026-11-07): login real dava 401 em tudo
- **Sintoma:** ao criar a conta e entrar no app, todas as chamadas à API voltavam 401 e o app encerrava a sessão com "Sua sessão expirou".
- **Causa:** o relógio do PC estava **729 s (~12 min) atrasado** em relação ao Supabase (comparado com o cabeçalho `Date` do servidor do Supabase). O token recém-emitido tinha `iat` "no futuro" para a API, e o PyJWT recusa isso (`ImmatureSignatureError: The token is not yet valid (iat)`, reproduzido localmente). Os testes não pegaram porque geram tokens com o relógio da própria máquina.
- **Correção em `security.py`:** o `iat` não é mais conferido (não protege nada que assinatura e `exp` já não protejam) e há tolerância de 30 s no `exp`. O motivo de cada recusa vai para o log do servidor (`Token recusado (<tipo do erro>): ...`), sem o token.
- **Testes:** 3 novos em `tests/test_security.py` (relógio atrasado 729 s aceito; tolerância pequena: vencido há 10 s passa, há 2 min dá 401; motivo no log sem o token). Os testes de "token vencido" passaram a usar 2 min. `pytest` → `354 passed`.
- **Ação do usuário:** sincronizar o relógio do Windows. Um relógio atrasado continua afetando outras coisas (datas de "hoje", look do dia, aceitar um token vencido há até 12 min).
